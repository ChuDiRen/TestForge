## 1. 背景与定位

### 1.1 背景

企业级测试团队在"用例从哪来、怎么保证全、怎么跑得动、怎么追得到"四个环节均有痛点：

- **设计靠经验**：测试用例质量依赖个人经验，边界值、异常路径、越权场景靠人脑枚举，覆盖不完整且不可度量；
- **知识散落各处**：需求文档（飞书/Confluence/docx）、代码、接口契约（OpenAPI/proto）、历史缺陷各自孤立，写用例要到处翻；
- **多服务知识难维护**：微服务架构下服务间调用关系、契约版本、业务流分散在几十个仓库，新人接手成本高，契约变更后下游用例大面积失效且无人知道影响面；
- **生成不可信**：直接拿 LLM 对着代码生成用例，检索漏一块就漏一批场景，且生成结果"看起来完整"，无法机器验证；
- **过程不可溯**：用例是谁、从哪个需求、基于什么上下文生成的，执行失败后无法回答"这个用例为什么长这样"。

### 1.2 产品定位

面向测试/研发团队的 **AI 测试用例生成与验证平台**，一句话概括：

> **需求是源头，知识预编译，AI 生成用例，沙箱验证闭环，全链路可回溯。**

平台不做通用测试管理（TestRail 类），不做 CI 替代品。核心价值链：**需求录入 → 知识编译（Wiki/契约） → 上下文组装 → 两阶段 AI 生成 → 沙箱执行验证 → 分层用例库 → 全链路追溯**。

### 1.3 目标用户与角色

| 角色 | 使用场景 |
| --- | --- |
| QA / 测试工程师 | 录入需求、评审 AI 生成的用例、维护用例库、查看执行结果 |
| 后端开发 | 仓库接入、契约变更后处理影响分析、消费生成的单测/接口测试 |
| 测试负责人 | 仪表盘质量指标、待人审队列、Wiki 健康度治理 |
| 产品 / PO | 需求录入、需求与实现冲突的确认 |
| 平台管理员 | 仓库凭据管理、沙箱集群、日志审计导出 |

### 1.4 产品目标（MVP 上线后 1 个月）

1. 从需求录入到结构化用例草稿入库，**全程无人工干预**（人工只做评审）；
2. AI 生成用例的**执行有效率 ≥ 85%**（编译通过 + 沙箱执行通过，含修复循环）；
3. 目标代码**分支覆盖率相对人工基线增量 ≥ 15%**；
4. 任一用例/执行结果可**反向回溯到需求源头**（traceID 查询 ≤ 5 秒）。

### 1.5 核心假设与不可替代性（第一原理）

生成可信的测试用例需要三件事：**完整的上下文（不能漏）、可执行的验证（不能骗）、可追溯的过程（不能丢）**。直接 RAG 检索三件事都保证不了。本平台的不可替代性：

1. **知识预编译而非查询时检索**：把 RAG 的"查询时实时检索"改为"导入时预编译"——代码库被编译成稳定、结构化、人可 review 的 Wiki（模块页/业务流页/函数卡片），上下文一致、生成结果可复现，解决 RAG 检索方差导致的"两次生成用例集不一样"；
2. **执行验证闭环**：生成→沙箱执行→失败反馈修复→覆盖率回填，机器兜底机器能兜的事，产出的是"验证过能跑"的用例而非文本；
3. **需求作为唯一源头 + 契约变更双向影响分析**：需求、代码（Wiki）、用例三方一致性检查，契约变更/需求变更自动算影响面并定向重生成——这是人工维护多服务用例集做不到的。

### 1.6 产研测分工与测试流程闭环（平台边界）

**产研测标准分工**（业界通用实践，平台按此对齐）：

| 阶段 | 产品 | 研发 | 测试 |
| --- | --- | --- | --- |
| 需求 | 输出 PRD、组织需求评审 | 参与评审（技术可行性） | 参与评审，输出测试点/疑问清单 |
| 设计/排期 | — | 设计文档、接口文档、排期 | 评估测试工时、制定测试计划 |
| 开发 | — | 编码 + 自测，输出提测单 | 用例设计与评审、准备数据/环境 |
| 提测 | — | 提测（自测通过为前提） | **冒烟测试（版本准入）** |
| 测试执行 | — | 修缺陷 | 执行用例、**缺陷生命周期管理** |
| 回归 | — | 修复提交 | **回归测试（平台自动触发）** |
| 准出/发布 | 验收 | — | **准出标准核对、测试报告** |
| 上线后 | 验收 | 线上问题修复 | 线上验证、复盘度量 |

**测试流程闭环主干**（本平台对齐）：

```
需求分析 → 测试计划 → 用例设计 → 用例评审 → 冒烟(准入) → 用例执行
→ 缺陷管理(新建→指派→修复→回归→关闭) → 回归测试
→ 准出标准核对(用例执行100% + 致命/严重清零 + 遗留有结论) → 测试报告 → 复盘
```

**平台覆盖边界**：

- **AI 自动化（平台核心价值）**：用例设计（生成+守卫）、用例执行（沙箱）、回归触发（缺陷关联自动回归）、缺陷创建（失败自动建）、准入/准出核对（标准自动判定）、报告初稿（LLM 撰写）；
- **人工主导（平台辅助）**：需求评审、用例评审（平台供草稿）、缺陷确认/指派、遗留评审、报告修订；
- **平台不做（对接即可）**：PRD 编辑与需求管理、研发排期/工时管理、环境部署——通过 REST/事件与项目管理系统（飞书项目/Jira）、CI 对接。

## 2. 核心技术决策

以下决策在需求梳理阶段确定，是全部功能设计的依据。

### 2.1 知识供给：Wiki 预编译为主干，RAG 为补充，源码为事实源

测试用例生成是**召回敏感（recall-critical）**任务：漏掉一个参数约束就漏一批边界用例。RAG top-k 检索保证精度不保证全量，且检索有方差。因此：

| 知识源 | 角色 | 说明 |
| --- | --- | --- |
| 源码注入（tree-sitter） | **ground truth** | 被测函数真实源码 + 直接依赖签名，必须原文注入 |
| 契约（OpenAPI/proto/topic） | 跨服务 ground truth | 服务边界处 AST 断裂，跨服务依赖一律走契约 |
| Wiki（预编译） | 全局语义主干 | 模块职责/业务规则/调用关系/业务流，人可 review |
| Trace 采样 | 真实数据 | 生产/预发链路真实报文（脱敏），边界值从真实分布反推 |
| RAG（相似用例） | few-shot | 检索存量相似测试，保持断言风格一致 |
| RAG（历史缺陷） | 避坑 | 缺陷模式注入，防止同一坑踩第二次 |

**上下文注入优先级（写死在 system prompt）：`code > contract > wiki > trace > similar > bugs`，冲突时以源码/契约为准。**

### 2.2 两阶段生成 + 覆盖守卫

LLM 不直接写代码：**阶段 A 产出用例清单（结构化 JSON）→ 静态覆盖守卫（边界/等价类/异常/权限五类检查表，缺类自动补）→ 阶段 B 按清单生成代码**。覆盖率与稳定性显著优于一步到位。

### 2.3 微服务多仓：契约注册中心 + 系统 Wiki 层

多仓不是单仓方案复制 N 份，需新增两层：

- **契约注册中心**（跨仓单一事实源）：OpenAPI / gRPC proto / Kafka topic 定义 + 版本 diff，breaking 变更自动识别；
- **系统 Wiki 层**（跨服务）：服务地图、业务流页、事件流、SLA（来自 trace），由 trace 数据反推生成。

### 2.4 交互协议：前端↔后端 HTTP，服务间 RPC

- **前端 ↔ 后端：HTTP/REST**（网关统一入口）；
- **服务 ↔ 服务：RPC（gRPC）**；
- 异步事件：Kafka（契约变更通知、用例入库通知等）。

## 3. 系统架构

### 3.1 总体架构

```
前端（本原型） ──HTTP/REST──▶ API Gateway / BFF ──gRPC──▶ 平台服务群
                                                              │
┌──────────────────────────────────────────────────────────────┤
│ repo-svc        仓库接入/拉取/webhook/凭据                     │
│ wiki-builder    tree-sitter 解析 + LLM 分层摘要 → repo/system Wiki │
│ contract-registry  契约注册/版本 diff/breaking 规则/影响分析    │
│ req-svc         需求录入/文档解析/规则抽取/Wiki diff/冲突检测    │
│ testgen-svc     上下文组装 + 两阶段生成 + 覆盖守卫               │
│ runner-svc      docker 沙箱执行 + 修复循环 + 覆盖率采集          │
│ trace-svc       全链路 traceID 日志（追加写，180 天）            │
└──────────────────────────────────────────────────────────────┘
              │                                    │
        数据面: Postgres(结构化) + 对象存储(wiki/日志归档) + 向量库(RAG)
```

### 3.2 HTTP REST 端点（前端 → 网关）

| 端点 | 用途 | 对应原型 |
| --- | --- | --- |
| `POST /api/repos` | 接入仓库 `{url, credential, branch, webhook}` | 仓库接入 |
| `POST /api/repos/{id}/pull` | 拉取 + 增量索引 + wiki 重建 | 仓库接入「拉取」 |
| `POST /api/requirements/ingest` | 需求录入 `{title, source, repoId, body\|fileId}` | 需求录入 |
| `POST /api/requirements/{id}/confirm` | 规则冲突确认 → 工单 + 定向重生成 | REQ-104「确认并重生成」 |
| `POST /api/generations` | 创建生成任务 `{target, layer, options}` | 生成工作台 |
| `GET /api/generations/{id}/events` | 生成进度（SSE 流式：PLAN→GUARD→CODE…） | 工作台管线动画 |
| `GET /api/cases` | 用例查询 `?layer=ut\|api\|fn\|e2e\|contract&module=&status=` | 用例库 |
| `POST /api/cases/{id}/review` | 人审通过/驳回 | 用例库状态流转 |
| `GET /api/runs` / `POST /api/runs/{id}/rerun` | 执行记录 / 重跑 | 执行记录 |
| `POST /api/contracts/{id}/impact` | 契约影响分析 → 受影响资产清单 | 服务地图影响面板 |
| `POST /api/plans` / `GET /api/plans/{iter}` | 迭代测试计划、准入/准出自动判定 | 测试计划 |
| `POST /api/defects` | 失败执行自动建缺陷（runner-svc 调用） | 缺陷管理 |
| `POST /api/defects/{id}/regression` | 触发缺陷自动回归（仅关联用例） | 缺陷管理 |
| `POST /api/reports/{iter}` | 生成测试报告（LLM 初稿） | 测试计划 |
| `GET /api/traces/{traceId}` | 全链路追溯查询 | 日志/追溯 |

### 3.3 gRPC 服务间接口（proto 骨架）

```protobuf
service WikiBuilder {
  rpc Rebuild(RepoDiff) returns (RebuildResult);     // 增量重建
  rpc GetModulePage(PageQuery) returns (WikiPage);
}
service ContractRegistry {
  rpc Register(Contract) returns (ContractVersion);
  rpc Impact(ContractDiff) returns (stream ImpactEvent);
}
service TestGen {
  rpc Generate(GenPlan) returns (stream GenEvent);   // PLAN→GUARD→CODE
  rpc RegenerateAffected(Scope) returns (GenResult);
}
service TestRunner {
  rpc Execute(TestSuite) returns (RunReport);        // docker 沙箱
}
service ReqIngest {
  rpc Parse(RequirementDoc) returns (ParseReport); // 规则+冲突检测
}
service DefectSvc {
  rpc CreateFromRun(RunFailure) returns (Defect);  // 失败自动建缺陷
  rpc TriggerRegression(DefectId) returns (RunReport);
}
service PlanSvc {
  rpc EvaluateExitPlan(Iteration) returns (ExitCheck); // 准入/准出自动核对
}
service TraceLog {
  rpc Append(TraceEvent) returns (Ack);              // 追加写
  rpc Query(TraceQuery) returns (stream TraceEvent);
}
```

## 4. 功能需求

> 每个功能标注对应原型视图。验收标准为该功能"做完"的判定条件。

### FR-1 仓库接入（原型：📥 仓库接入）

**描述**：多仓库批量接入，Git 拉取后自动执行索引流水线。

**规则**：
1. 支持批量注册仓库（Git URL + 凭证 + 分支）；凭证（SSH deploy key / Access Token）由凭据管理器托管，**不落明文**；
2. 拉取 = `git pull --ff-only` + tree-sitter 增量索引 + wiki 重建 + 契约扫描 + RAG 增量向量化，一条流水线自动完成；
3. 触发方式：手动、webhook（push 事件增量）、定时全量（默认 30 分钟）；
4. 拉取/克隆过程输出结构化日志（构建体系识别、函数/端点/调用图计数、wiki 页数、契约数），前端实时展示；
5. 拉取失败（凭据过期、网络）状态可见并可重试。

**验收**：填 URL → 克隆 → 表格出现新仓库且状态"已接入"；日志展示全流水线步骤；服务地图、仪表盘、Wiki 健康度同步更新。

### FR-2 Wiki 编译层（原型：📚 代码库 / Wiki）

**描述**：导入时预编译——把代码库和跨服务知识编译为"人可 review 的 Markdown + 机器可查的结构化索引"。

**规则**：
1. 两层结构：**repo Wiki**（总览页 → 模块页 → 函数卡片）+ **系统 Wiki**（服务地图说明页、业务流页）；
2. 模块页内容：职责、对外接口、业务规则、调用关系、已知风险点（来自历史缺陷）；业务流页内容：跨服务链路、关键规则、SLA（来自 trace 采样）、契约依赖、关联用例；
3. 产物双份：Markdown（人审）+ 结构化索引 SQLite/Postgres（函数→模块→调用方，供上下文组装精确查询）；
4. **增量重建**：git diff → 只重建受影响函数卡片与模块页，调用方页面标记 `stale`；
5. stale 页面横幅告警 + 一键重建，重建后 rev +1。

**验收**：源码变更后相关页面自动标 stale；重建只触达受影响页面；业务流页展示 SLA 与契约依赖（含 breaking 告警）。

### FR-3 服务地图 / 契约中心（原型：🗺 服务地图 / 契约）

**描述**：跨仓单一事实源的可视化与治理。

**规则**：
1. 服务依赖图：节点=服务，实线=同步调用（前端→网关 HTTP/REST、服务间 gRPC），虚线=异步事件（Kafka），边上标契约名+版本；
2. 契约注册中心：REST / gRPC / topic 三类契约，提供方、版本、消费方、最近变更；
3. **breaking 变更检测**：CI 契约 diff 命中 breaking 规则 → 图上红色流动虚线告警；
4. **影响分析**：点击变更边 → 影响传播链（提供方发布 → 消费方 wiki 标 stale → 关联用例打标）+ 受影响资产清单（用例级、wiki 页级）；
5. 影响确认后支持**定向重生成**受影响用例（只重生成交互中变更的 5 个，非全量）。

**验收**：构造契约 breaking diff → 地图标红 → 影响面板列出受影响用例与 wiki 页 → 一键定向重生成 → 执行记录/用例库状态联动更新。

### FR-4 需求录入（原型：📝 需求录入）——**全流程唯一源头**

**描述**：一切项目的源头是用户需求。需求必须绑定目标仓库/服务，录入后自动编排后续全部环节。

**规则**：
1. 录入渠道：上传文件（.md/.docx/.pdf）、飞书文档、Confluence、直接粘贴（用户故事 + 验收条件模板）；
2. **必选关联仓库**（需求驱动哪个服务的测试）；
3. 解析管线四步：① 文档解析 → ② 规则抽取（用户故事/业务规则/验收条件/角色权限/边界候选）→ ③ **Wiki diff**（与系统 Wiki 业务流页对比，新规则待确认）→ ④ 用例生成；
4. **三方一致性检查**：需求 vs 代码实现（Wiki 与代码一致时以实现为参照）冲突时标记"规则冲突"，给出影响面与处理建议（更新 wiki 规则页 → 生成配置变更工单 → 定向重生成受影响用例），由人一键确认；
5. 解析完成后**自动编排**：生成用例草稿 → 沙箱执行 → 回填需求状态，全程无需人工干预（人工只评审）；
6. 需求状态机：`解析中 → 待人审 / 规则冲突待确认 → 已生效`。

**验收**：粘贴用户故事 → 四步管线跑完 → 需求列表新增行且状态待人审；用例库出现关联草稿用例；构造与实现矛盾的需求（如关单 15min→10min 但代码为 15min）→ 被标记冲突，确认后 wiki 规则页更新、工单创建、受影响用例重生成，全部动作进日志。

### FR-5 生成工作台（原型：🛠 生成工作台）

**描述**：单目标用例生成的核心管线，六路上下文 + 两阶段生成 + 沙箱验证闭环。

**规则**：
1. 目标按层选择：单元（函数）/ 接口（端点）/ 功能（业务流）/ E2E（旅程）；
2. **上下文组装预览**（六路，按优先级注入）：Wiki 页 / 源码注入 / 相似用例 RAG / 历史缺陷 / 契约 / Trace 采样；
3. 五步管线：① 用例清单 PLAN（纯 JSON，schema 校验）→ ② 覆盖守卫（静态检查表：边界/等价类/异常/权限，缺类自动补）→ ③ 代码生成（按清单，pytest/JUnit/httpx/Playwright）→ ④ 沙箱执行（docker `--network none` + 资源限额）→ ⑤ 覆盖率回填；
4. **修复循环**：沙箱失败用例（报错 + 实际响应）回填 prompt 重新生成，≤ 3 轮；
5. **覆盖率缺口定向补用例**：分支未覆盖 → 生成补齐；
6. 生成产出结构化用例表（每条：ID/类别/输入/预期/覆盖分支/状态），点行看可执行 JSON。

**验收**：点击生成 → 管线动画与日志逐步推进 → 产出 9 用例、首轮 7 通过、修复 2、分支覆盖 92%（mock 基准）；守卫检出缺权限类用例自动补；每条用例 JSON 可直接喂给 runner。

### FR-6 用例库（原型：🗂 用例库（分层））

**描述**：五层用例统一管理，全部为可执行 schema（**禁止自然语言步骤**）。

**规则**：
1. 分层：单元测试 / 接口测试 / 功能测试 / E2E 测试 / 契约测试（消费方契约，Pact 风格）；
2. 用例 schema 示例（API 层功能用例）：

```json
{
  "id": "FUNC-001",
  "title": "下单金额为负数应拒绝",
  "module": "订单模块",
  "category": "exception",
  "precondition": [{"type": "db_seed", "fixture": "user_balance_100"}],
  "steps": [
    {"action": "api_call", "method": "POST", "path": "/api/orders",
     "body": {"sku": "A1", "amount": -1}, "as_user": "buyer"}
  ],
  "expected": [
    {"type": "status", "value": 400},
    {"type": "json_path", "path": "$.code", "value": "INVALID_AMOUNT"}
  ],
  "runner": "httpx",
  "source": "REQ-105"
}
```

3. 各层执行方式：单测 pytest（docker 沙箱）/ 接口 httpx / 功能 httpx 或 Playwright / E2E Playwright（staging 全真实服务）/ 契约 Pact（消费方侧，broker 回写）；
4. 筛选：层级 tab（计数实时）× 模块 × 类别（normal/boundary/exception/permission/contract）× 状态（草稿/待人审/已入库）；
5. 每条用例带 `source`（来源需求）与 trace 字段。

**验收**：层级 tab 切换计数正确；需求解析后草稿自动出现在对应层；用例详情 JSON 结构完整可直接执行。

### FR-7 执行记录（原型：🧪 执行记录）

**描述**：所有沙箱执行的统一台账。

**规则**：
1. 记录：Run ID、目标、触发方式（手动/PR/定时/webhook/需求驱动编排/影响分析/契约变更）、沙箱状态、通过率、覆盖率、修复轮次、耗时、状态；
2. run 详情：沙箱参数、时间线（首轮→修复→终态）、覆盖率缺口、**关联 traceID 与源头需求**；
3. 失败 run 进入修复循环自动处理，超 3 轮转人工。

**验收**：任意联动操作产生的 run 实时出现在列表顶部；详情可反向回溯到需求。

### FR-8 日志 / 追溯（原型：📜 日志 / 追溯）

**描述**：一切操作皆日志，traceID 全链路贯穿。

**规则**：
1. 记录范围：需求（录入/解析/diff/确认）、生成、执行、仓库（接入/拉取）、契约（diff/影响）、**缺陷（创建/回归/关闭）**、**计划（准入/准出/报告）** 八大类；
2. 每条日志：时间、traceID、类型、操作者（人 or `req-svc`/`testgen-svc`/`runner-svc`/`ci-bot`）、摘要、源头需求；
3. **双向回溯**：正向——需求追到执行结果；反向——执行/用例通过 traceID 回溯到需求源头。链路以树形展示（`├─/└─` 时间线）；
4. 链路抽屉提供跳转：去源头需求 / 去用例库 / 去执行记录；
5. 支持按类型筛选、按 traceID/需求/关键词搜索；日志保留 180 天，可导出审计包。

**验收**：搜索 `tr_8a2f` 能看到从"QA-张三 需求录入"到"RUN-0425 执行 10/10"的完整链路；任意联动操作后日志实时新增；执行详情可跳回需求。

### FR-9 全局联动与仪表盘（原型：📊 仪表盘 + 顶栏）

**描述**：跨视图状态共享，任何操作的数据变化全局同步。

**规则**：
1. 顶栏常驻「待人审 N」，任何影响待审数的操作全局同步；
2. 仪表盘四卡：用例有效率 / 分支覆盖率增量 / 本周生成用例（按层拆分）/ 待人工评审；
3. 联动矩阵（触发 → 自动更新的位置）：

| 触发 | 联动 |
| --- | --- |
| 需求解析完成 | 需求列表 +行；用例库 +草稿行、层级计数刷新；待审数变化；自动编排 run 入执行记录；日志链路写入 |
| 影响分析定向重生成 | 执行记录 +run；用例状态翻已入库；待审 -1；日志写入 |
| 工作台生成完成 | 执行记录 +run；本周生成用例数 +N；日志写入 |
| 仓库克隆/拉取 | 服务地图 +节点；仪表盘 Wiki 健康度 +行；接入仓库数变化；日志写入 |
| 需求冲突确认 | wiki 规则页更新；工单创建；受影响用例重生成 + run；需求状态翻已生效；日志写入 |
| 执行失败（超修复轮次） | **自动创建缺陷并指派**；缺陷表 +行；日志写入 |
| 缺陷修复提交/回归验证 | **自动重跑关联用例 +run**；通过即关闭缺陷；日志写入 |
| 准入/准出核对、报告生成 | 迭代轮次与准出状态更新；报告归档；日志写入 |

4. Wiki 健康度面板：各仓库最新/stale 状态 + 一键重建全部 stale 页面。

### FR-10 测试计划与轮次（原型：🎯 测试计划）

**描述**：以迭代为纲组织测试闭环，准入/准出由平台按标准自动判定。

**规则**：
1. 迭代绑定：版本号 + 关联需求 + 用例集（按五层计数，从用例库实时汇总）；
2. 测试轮次：**冒烟（版本准入）→ 功能执行 → 回归**，各轮次状态实时可见；
3. **准入自动判定**：冒烟测试通过 + 用例评审通过率 ≥ 阈值（默认 90%）→ 已准入；不通过自动打回研发；
4. **准出自动判定**：用例执行 100% + 致命/严重缺陷修复并验证 + 遗留缺陷有评审结论 + 测试报告已输出；
5. 测试报告：平台自动汇总执行数据（按层）、缺陷统计与遗留分析、AI 质量度量（生成占比/有效率/覆盖率增量），**LLM 出报告初稿，人工可修订后归档**；支持中期报告与终版。

**验收**：迭代页可见准入/准出状态自动计算；点「测试报告」→ 日志展示汇总过程 → 报告 JSON 含用例/缺陷/AI 度量与结论。

### FR-11 缺陷管理闭环（原型：🐞 缺陷管理）

**描述**：测试执行失败的自动闭环，是测试流程闭环的核心环。

**规则**：
1. **失败自动建缺陷**：沙箱执行失败（超修复轮次）→ runner-svc 自动创建缺陷，四向关联：run、用例、源头需求、traceID，并按服务目录自动指派研发；
2. 生命周期：`新建 → 已确认/指派 → 修复中 → 待回归 → 已关闭`；拒绝/延期需评审结论，计入准出遗留分析；
3. **自动回归**：修复提交（PR 合并/工单完成）→ 平台**只重跑缺陷关联用例**（非全量）→ 通过自动关闭、失败自动重开；
4. 缺陷与契约影响分析联动：契约变更导致的失败自动关联影响 trace。

**验收**：BUG-302「回归验证」→ 日志展示"定位关联用例 → 沙箱重跑 → 通过关闭"；run 入执行记录、日志写入；准出时"致命/严重清零、遗留有结论"自动核对。

### FR-12 测试报告与复盘（原型：🎯 测试计划）

**描述**：测试闭环的出口与度量沉淀。

**规则**：
1. 报告内容：用例统计（按层执行率/通过率）、缺陷统计与遗留风险分析、准入/准出逐项核对结论、AI 质量度量（生成占比/有效率/覆盖率增量/评审通过率）；
2. 生成方式：平台汇总结构化数据 + LLM 撰写初稿 + 人工修订归档；
3. 迭代复盘：准入率、缺陷回归及时率、AI 生成占比趋势进仪表盘历史。

**验收**：中期/终版报告一键生成，数据可追溯到每条用例与缺陷。

## 5. 关键业务流程

### P1 需求驱动全流程（主流程）

```
需求录入(绑定仓库) → 文档解析 → 规则抽取 → Wiki diff(冲突检测)
  → [冲突?] → 人工确认 → wiki 规则页更新 + 工单
  → 自动编排生成(六路上下文+两阶段+守卫) → 沙箱执行(修复循环≤3轮)
  → 用例草稿入分层用例库 → 人审 → 已入库 → 结果回填需求状态
全程 traceID 贯穿，日志可回溯
```

### P2 契约变更影响分析

```
提供方发布新版本 → 契约注册中心 diff → 命中 breaking 规则
→ 定位受影响消费方 → 消费方 wiki 页标 stale + 关联用例打标
→ 影响面板(传播链+资产清单) → 定向重生成(仅受影响用例)
→ 沙箱回归 → 消费方契约测试回写 broker → 日志归档
```

### P3 仓库接入

```
录入 Git URL + 凭据 → git clone/pull → 构建体系识别
→ tree-sitter 索引(函数/端点/调用图) → wiki 编译(总览+模块页+函数卡片)
→ 契约扫描注册 → RAG 向量化 → 服务地图加节点 + 各视图联动
```

### P4 缺陷闭环（测试流程闭环的核心环）

```
用例执行失败(超修复轮次) → 自动创建缺陷(关联 run/用例/需求/traceID) → 指派研发
→ 修复提交 → 平台自动回归(仅关联用例) → 通过: 关闭 / 失败: 重开
→ 准出时缺陷遗留评审 → 计入测试报告
```

### P5 提测准入 → 准出

```
研发提测单 → 冒烟测试(平台自动跑冒烟集) → 通过: 准入 / 失败: 打回研发
→ 功能轮执行(缺陷闭环见 P4) → 回归轮
→ 准出核对: 用例执行 100% + 致命/严重清零 + 遗留有结论 + 报告输出
→ 测试报告(LLM 初稿+人工修订) → 发布
```

## 8. 里程碑规划

| 阶段 | 范围 | 说明 |
| --- | --- | --- |

## 9. 风险与对策

| 风险 | 对策 |
| --- | --- |
| Wiki 过期导致生成错误用例 | 挂 commit/webhook 增量重建 + 被测源码原文注入（wiki 只当上下文）+ 执行验证兜底 |
| RAG 漏召回导致漏场景 | 预编译为主、RAG 只做 few-shot 补充；覆盖守卫静态检查表兜召回 |
| LLM 幻觉（编造不存在的字段/接口） | 契约/源码为 ground truth + JSON schema 校验 + 沙箱执行验证 |
| 契约治理缺位（没人看 breaking） | 影响分析自动化 + 消费方 owner 通知 + 定向重生成降低处理成本 |
| E2E flaky 污染失败反馈闭环 | E2E 放最后；失败自动截图 + trace 归档；数据池用脱敏 trace 采样 |
| 多仓 wiki 维护成本爆炸 | 影响分析自动化 + stale 自动标记 + 定向重建，杜绝人肉盯联动 |

## 10. 原型说明

- **文件**：`testforge-prototype.html`（单文件、零依赖、浏览器直接打开）
- **9 个视图**：仪表盘 / 代码库·Wiki / 服务地图·契约 / 仓库接入 / 需求录入 / **测试计划** / 生成工作台（核心）/ 用例库（分层）/ 执行记录 / **缺陷管理** / 日志·追溯 / **需求质量流水线**
- **联动**：全局状态对象驱动六条联动链路（见 FR-9），顶栏「待人审」全局同步
- **演示动线**：需求录入（源头）→ 日志/追溯看 traceID 全链路 → 点链路回溯 → 服务地图点红色 breaking 边看影响分析 → 定向重生成 → 执行记录看结果 → **缺陷管理点「回归验证」看缺陷闭环 → 测试计划生成测试报告**
- **URL 直达参数**：`?view=workbench&autorun=1`（生成动画）、`?view=map`、`?view=logs`、`?view=wiki&stale=1`、`?view=wiki&wikipage=flow`、`?view=plans`、`?view=defects`
- **平台架构呈现**：服务地图页含架构条（前端→HTTP→网关→gRPC→服务群）与「平台对接契约」面板（REST 端点 + proto 骨架），真实开发按此对齐

## 11. 需求质量保障流水线（提效 × 质量）

> 设计原则：**一切以需求为单位**。需求进入平台即进入质量流水线，AI 自动判定与推进全部关卡；**人的介入只发生在例外与决策**。提效不是靠人少做事，而是靠"AI 推进 + 人只在例外介入"——质量由关卡保障，提效由自动化率保障。

### 11.1 六道质量关卡（G0~G5，AI 自动判定与推进）

| 关卡 | 名称 | AI 自动判定标准 | 人介入条件（例外） |
| --- | --- | --- | --- |
| G0 | 可测性准入 | 可测性评分 ≥ 80（二义性/完整性/验收条件可验证）；不达标**自动打回产品**并附修订建议 | 无——打回由 AI 完成，不耗测试人力 |
| G1 | 知识就绪 | 绑定仓库 wiki 编译完成 + 契约注册 ≥ 1 | wiki 编译失败（环境类） |
| G2 | 用例覆盖 | 生成用例过覆盖守卫，预估分支覆盖 ≥ 基线 +15% | — |
| G3 | 执行验证 | 沙箱执行（含修复循环 ≤ 3 轮）全部通过 | 修复 3 轮仍失败 → 自动建缺陷转人工 |
| G4 | 缺陷清零 | 关联缺陷全部关闭，或遗留有评审结论 | 遗留缺陷评审 |
| G5 | 准出报告 | 报告自动生成 + 发布风险建议 | **发布拍板——人唯一必须到场的决策** |

### 11.2 需求质量档案（每个需求一份，覆盖率 100%）

每条需求自动沉淀质量档案：六关卡时间线（AI 每步判定依据与完成时间）、人工介入记录（谁/何时/为什么）、最终质量分（**可测性 × 覆盖 × 执行 × 缺陷 加权**）。质量分跌破阈值自动预警。档案即需求的质量"体检报告"，发布评审直接引用。

### 11.3 提效度量（每个需求自动统计，进仪表盘）

| 指标 | 传统人工 | TestForge |
| --- | --- | --- |
| 单需求测试人力投入 | 5~8 人日 | **≤ 0.5 人日**（评审抽样 + 例外处理） |
| 需求 → 可测周期 | 3~5 天 | **4~8 小时**（自动推进） |
| 环节自动化率 | — | ≥ 90%（G0 打回等全程无人工） |
| 人工介入密度 | 全程介入 | ≤ 2 次/需求（例外 + 拍板） |
| 需求问题暴露时点 | 执行期（浪费 2~3 人日） | 录入后 30 秒（G0 即拦截） |

### 11.4 人的三种角色（从执行者变为决策者）

1. **定标准**：维护阈值与守卫规则（可测性分数线 80、覆盖率基线 +15%、置信度阈值 0.95、守卫检查表）——标准定好，AI 按标准自动把关，标准即质量策略；
2. **批例外**：只处理 AI 抛出的例外——低置信产物（< 0.95 进人审队列并按置信度排序）、需求与实现冲突、修复 3 轮失败、遗留缺陷评审；
3. **拍发布**：G5 发布决策（AI 给风险建议与数据引用，人签字）。

### 11.5 信任与反馈闭环

- **置信度前置**：AI 产出全部带置信度，高置信自动流转，低置信进例外队列（按置信度排序，人先审最没把握的）；
- **修正回流**：评审驳回原因 → 生成 few-shot；分诊纠正 → 分类器校正；建议否决 → 规则回流——人的每次修正让自动化率继续上升；
- **度量可见**：自动化率、例外密度、质量分分布、AI 评审通过率进仪表盘，自动化率是平台自身的北极星指标。

### 11.6 AI 提效组件清单（六关卡的能力底座）

| 组件 | 提效点 | 服务关卡 |
| --- | --- | --- |

| 失败分诊 | 环境/脚本类失败自动处理，误报不进缺陷队列 | G3/G4 |
| 精准回归圈定 | 缺陷回归只跑关联用例，回归从全量天级降到分钟级 | G4 |
| 报告初稿 | 准出核对 + 报告自动生成，报告从半天到 1 分钟 | G5 |
| Wiki 预编译 + 巡检 | 知识就绪自动化，stale 主动预警 | G1 |
| 置信度分流 | 高置信自动放行，人工只看低置信项 | 全部关卡 |
