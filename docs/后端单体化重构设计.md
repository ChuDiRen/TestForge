# 后端单体化重构设计（传输层剥离 + FastAPI 分层重组）

> 状态：**已实施（2026-10-10）** · 回归证据：131 pytest 全绿 · ruff/mypy 全绿 · 前端 build 绿 · 真实网关登录冒烟全通（7 服务 all_green，177 用例/804 Wiki 页数据完好）
> 实施口径：传输层剥离与本方案一致；目录按经典 FastAPI 分层骨架（app/main + core/api/models/db/services）物理重组，`services/*/api.py` 即原 RPC 契约的平铺函数形态。

## 0. 结论先行

**你的判断对了一半，先澄清一个事实**：TestForge 现在**就是**单体运行——`MONO_MODE=1` 是默认值，9 个业务服务全部进程内直调，生产部署只有一个进程、一个端口（8000）。「网关」不是独立部署的网关服务器，它就是那个唯一服务本身；「9 个业务服务」也不是 9 个进程，只是按 proto 服务边界组织的 Python 模块。

真正多余的不是网关和业务服务，而是它们之间的 **gRPC/proto 协议层**：单体模式下每次调用仍要构造 protobuf 请求对象 → 字符串方法名 dispatch → FakeContext 模拟 gRPC abort。协议层只在这一种情况下有价值：未来真的要把服务拆成多进程独立部署。以当前产品形态（本地/企业内单机部署、单团队维护），这个开关是 YAGNI。

**建议：做「传输层剥离」重构**——保留网关（HTTP 层）和业务模块的代码边界，删掉 proto/gRPC/mono 整个传输层，服务调用变成普通 Python 函数调用。HTTP API 面**零变化**，前端**零改动**。

## 1. 为什么要剥（实测依据）

| 现状 | 数字 | 问题 |
|---|---|---|
| 传输层专属代码 | **≈2200 行**：proto 386 + pb2 生成物 1569 + grpc_client 151 + mono 74 + grpc_server 34 | 每次改接口要 `make proto` 重新生成、维护 fix_proto_imports 补丁脚本 |
| 网关调用点 | 30 处 `grpc_call/grpc_stream`，分布 7 个文件 | 每个调用点都要：构造 pb2 请求对象 → 字符串方法名 → 解包响应 |
| 调用链间接性 | gateway → grpc_call → mono.dispatch(字符串) → servicer → service 函数 | 排障时调用栈多两层假抽象；类型检查器无法跨层追踪 |
| 双份接口定义 | 同一能力在 proto RPC + HTTP 路由各定义一遍 | proto 定义对前端/用户毫无可见性，纯内部成本 |
| 微服务模式使用率 | 0（从未在生产用过 MONO_MODE=0） | grpcio/grpcio-tools/protobuf 三个依赖 + 端口 50051~50057 管理全为这个模式陪跑 |
| 测试侵入 | 仅 1 处 monkeypatch grpc_call（test_repair_loop） | 迁移成本极低 |

**保留的价值盘点**（诚实列出，避免误伤）：
- proto 作为**设计文档**的价值 → 迁移后由「服务层函数签名 + pydantic 模型」承担，更准确（代码即文档）。
- 微服务演进可能性 → 模块边界不变，未来若真要拆，在同一批函数签名下重新插一层传输（gRPC/HTTP/队列）即可，且那时能按真实瓶颈选协议，而不是现在预付成本。
- gRPC 流式 → Python 生成器完全等价替代（见 §4）。

## 2. 目标形态

```
重构前                                  重构后
─────────────────────────────          ─────────────────────────────
gateway/ (HTTP 路由)                    gateway/ (HTTP 路由，唯一入口)
   ↓ grpc_call(字符串方法名, pb2对象)       ↓ 直接 import 函数调用
grpc_client / mono (传输层)             （删除）
   ↓                                    services/
services/*/main.py (gRPC Servicer)         repo/        service.py（原 repo_svc/service.py）
   ↓ pb2 消息                              wiki/        service.py + summarizer + analytics + ask
services/*/service.py (业务逻辑)            contract/    service.py
                                           req/         parser
                                           testgen/     context/planner/guard/probe/codegen/agent/web*
                                           runner/      service + sandbox
                                           trace/       main + defect_svc + plan_svc（保持同包）
                                        （各服务 main.py Servicer 适配层删除，
                                          业务函数改为 pydantic 入参/出参）

删除：proto/ · shared/gen/ · grpc_client.py · grpc_server.py · mono.py
      GRPC_PORTS 配置 · mono 开关 · make proto · fix_proto_imports.py
      依赖 grpcio / grpcio-tools / protobuf

保留不动：FastAPI 网关与全部 HTTP 路由 · shared 其余公共层（rag/kg/llm/db/auth/…）
          jobs 队列 · 沙箱 · MCP server（stdio 独立，本就不走 gRPC）· Ollama 兼容层 · 前端
```

分层原则不变：**routes（HTTP 适配）→ services（业务）→ shared（基础设施）**。变的只是层间协议：pb2 消息 + 字符串 dispatch → pydantic 模型 + 直接函数调用。

## 3. RPC → 函数映射表（16 个 RPC 全量）

| RepoSvc.RegisterUpload | repo_upload.py | `repo.register_upload(name, source_dir, branch) -> RegisterResult` |
| RepoSvc.Pull | main.py, regression.py | `repo.pull(repo_id) -> PullResult` |

| ContractRegistry.Register | contracts.py | `contract.register(name, type, provider_repo, version, spec, consumers) -> Contract` |
| ContractRegistry.Impact(stream) | contracts.py | `contract.iter_impact(contract_id, to_v) -> Iterator[ImpactEvent]` |

| TestGen.RegenerateAffected | generations.py, test_repair_loop | `testgen.regenerate_affected(repo_id, target_function, code_file, reason) -> RegenerateResult` |
| TestRunner.Execute | generations.py, regression.py | `runner.execute_suite(workspace, code_file, cov_pkg, ...) -> RunReport` |
| TraceLog.Append | shared/trace.py | `trace_svc.append(type, actor, summary, trace_id, req_code, extra)` |

## 4. 关键机制的等价替换

| 机制 | 现状（gRPC 形态） | 单体等价物 |
|---|---|---|
| 流式生成事件 | `Generate()` server-stream，网关 `grpc_stream()` 逐条读 | `Iterator[GenEvent]` 生成器，SSE 端点直接 for 循环消费（更简单，无超时重试层） |
| trace_id 传播 | gRPC metadata `x-trace-id` + 拦截器恢复 | **contextvars**（logutil 已有 contextvars trace_id 基础，middleware 已注入）——服务层直接读 contextvar，拦截器删除 |
| 错误传播 | `context.abort(code, msg)` / MonoRpcError | 普通 Python 异常（保留现有 ApiError 体系；服务层自定义异常直接穿透到路由 handler） |
| Ping/健康探测 | 9 个 Servicer.Ping + db_ok | 各服务模块 `ping()` 函数；`/api/system/services` 遍历调用，输出结构不变 |
| trace.py emit 降级 | 经 TraceLog gRPC 落库，失败降级直写 DB | 直接调 trace_svc.append（同一进程内调用不可能"失败降级"，删掉降级分支） |
| 超时/重试 | grpc_client 的 UNAVAILABLE/DEADLINE 重试 | 删除（进程内调用无需网络重试） |

## 5. 迁移步骤（每步全量可验证）

1. **服务层签名改造**：各 `services/*/service.py` 业务函数从 pb2 入参改为 pydantic/kwargs；Servicer main.py 变成兼容壳（内部转发新签名）。跑 130 pytest 确认绿。
2. **网关调用点切换**：30 处 `grpc_call/grpc_stream` 逐一换成直接函数调用（流式改生成器消费）；`shared/trace.py` 改直调。跑 pytest + TestClient 路由冒烟。
3. **删除传输层**：proto/、gen/、grpc_client/grpc_server/mono/base-pong、`make proto`、fix_proto_imports.py、GRPC_PORTS、`mono` 配置项、依赖三件套（uv lock 更新）、dev 脚本里微服务端口检查、docker-compose 微服务注释段。跑 pytest + ruff + mypy。
4. **端到端回归**：make dev 起服务 → 登录冒烟（健康/服务列表/仓库/Wiki/生成/检索中心）→ 前端 build（前端零改动但确认 API 面没动）。
5. **文档同步**：架构设计（删 gRPC 层图/表、MONO_MODE 机制节、9 服务→模块清单）、PRD §3、部署文档；接口设计**不变**（HTTP 面零变化）。

## 6. 风险与对策

| 风险 | 对策 |
|---|---|
| 生成事件 SSE 断线回放逻辑隐含 gRPC 流语义（600s 超时、ping 帧） | 回放数据源本就是 generation_events 表，与传输层无关——SSE 端点行为不变，重点回归该端点 |
| trace 中间件与 contextvars 传播在后台线程（jobs worker、doc_pipeline）失效 | jobs/doc_pipeline 均在网关进程内起线程；contextvars 需在任务入队时显式透传 trace_id（现在 payload_json 里已带 trace_id，链路不断） |
| 隐藏的 pb2 依赖漏删 | 以 `grep -r "pb2\|grpc" --include="*.py"` + mypy 全绿 + 启动冒烟三重确认 |
| 未来真要拆微服务 | 模块边界（9 个服务包）原样保留，函数签名即契约——届时在签名下插传输层即可，损失为零 |

## 7. 预期收益

- **净删 ≈2200 行**传输层代码 + 3 个依赖 + 1 个 Makefile target + 端口管理；
- 新接口改动从「改 proto → make proto → 改 servicer → 改路由」四步变「改函数签名 → 改路由」两步；
- 调用栈、类型检查、调试断点全链路直达，排障成本下降；
- 部署叙事变干净：**一个进程、一个端口、一份配置**（文档口径同步简化）。

## 8. 明确不做的事

- 不合并业务模块代码（9 个服务包的边界就是未来演进的期权，保留）；
- 不改 HTTP API 面（127 个接口、信封、SSE 协议全部不动，前端零改动）；
- 不动 MCP server / Ollama 兼容层 / jobs 队列 / 沙箱（与传输层无关）；
- 不引入新的进程间机制（Celery/消息队列等——jobs 表队列够用）。
